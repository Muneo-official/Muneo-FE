# 어드민 작업 내역 — 무엇을 추가했고 어디까지 확인했는가

2026-10-10 기준. 이번 어드민 작업의 핵심은 **기존 사용자 관리 화면에, 각 사용자가 저장한 예상 견적·견적서 진단·진단 피드백을 조회하는 기능을 추가한 것**이다. 실제 서버 호출 코드와 로컬 가상 QA 모드를 모두 만들었으며, 두 실행 모드는 데이터 출처가 다르다.

## 1. 기존 기능과 이번 추가 작업

| 구분                          | 내용                                                                                                                                                          |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 기존에 있던 기능              | 관리자 로그인 화면·로그인 API 호출, 사용자 목록·검색·필터, 사용자 상세 계정 정보, 계정 정보 수정·권한 변경·탈퇴·복구                                          |
| 이번에 새로 추가              | 사용자 상세의 ‘사용자 이용 내역’, 예상 견적·견적서 진단·진단 피드백 조회, 페이지 이동·새로고침·오류 처리, 관리자 조회 API 3개 호출 및 응답 검증, 가상 QA 모드 |
| 기존 기능 보완                | 서버 기준 관리자 세션 확인, 로그아웃 처리, 계정 전환 시 조회 데이터 초기화, 사용자 상세 진입 버튼 접근성                                                      |
| 백엔드 명세 수령 후 추가 보완 | 오류 코드별 안내, 문자열 견적 범위 표시, 테스트 확대, 배포 OpenAPI와 실제 호출 경로 대조                                                                      |

지금 사용자 목록 화면의 이름을 눌러 **사용자 상세 → 사용자 이용 내역**으로 들어가면 이번에 추가한 주요 기능을 확인할 수 있다.

## 2. 작업 단위 A — 사용자별 이용 내역 화면

| 메뉴        | 운영자가 확인할 수 있는 내용                                                                                                             |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 예상 견적   | 사용자가 저장한 견적의 ID·저장일·사용자 ID, 지역·평수·공간 유형·선택 공정 등 저장된 입력, 총 예상 견적, 서버가 저장한 결과 전체          |
| 견적서 진단 | 진단 ID·저장일·사용자 ID, 업체명 등 저장된 입력, 진단 제목, 응답에 포함된 확인 항목 수, 공정별 항목의 상태·설명·가이드, 저장된 결과 전체 |
| 진단 피드백 | good/bad, 선택 이유의 한국어 표시, 자유 의견, 연결된 진단 ID, 생성일·마지막 수정일                                                       |

각 기록은 눌러 펼치는 방식이다. 복잡한 결과도 확인할 수 있도록 예상 견적과 진단에 ‘저장된 결과 전체 보기’를 두었다. 서버에 있는 저장 결과를 조회하며 화면을 열 때 AI 진단을 다시 실행하지 않는다. 날짜는 시간대가 포함된 API 응답을 한국 시간으로 변환해 표시한다.

예를 들어 사용자가 ‘A업체 견적서’를 진단·저장하고 ‘아쉬워요 / 설명이 이해하기 어려워요’라는 피드백을 남겼다면, 운영자는 해당 사용자의 상세 화면에서 진단 결과와 연결된 피드백을 대조할 수 있다.

이번에 추가한 이용 내역 기능은 **조회용**이다. 관리자가 이 화면에서 사용자의 견적 결과나 피드백을 수정·삭제하는 기능은 추가하지 않았다. 사용자 본인의 피드백 수정·삭제는 고객용 웹에서 처리한다.

## 3. 작업 단위 B — 실제 백엔드 API 연결

선택한 사용자 ID로 다음 세 API를 호출하도록 구현했다.

| 메뉴        | 연결한 API                                      |
| ----------- | ----------------------------------------------- |
| 예상 견적   | `GET /api/v1/admin/users/{userId}/estimates`    |
| 견적서 진단 | `GET /api/v1/admin/users/{userId}/risk-reports` |
| 진단 피드백 | `GET /api/v1/admin/users/{userId}/feedback`     |

공통 요청은 `page=0&size=10`부터 시작한다. API의 인증 쿠키를 포함하고 응답의 `result.content`를 표시한다. 전체 건수와 페이지 정보는 서버 응답을 사용한다. 기록 정렬은 백엔드 명세의 생성일 내림차순·ID 내림차순을 따른다.

일반 개발 모드에서는 브라우저의 `/api` 요청을 Vite 개발 프록시가 백엔드로 전달한다. `VITE_API_BASE_URL`로 대상을 지정할 수 있고 현재 기본값은 `https://api-dev.muneo.kr`다. 운영 빌드에서는 이 환경변수로 설정한 API 주소를 사용한다.

모노레포 자체가 사용자 데이터를 공유해 주지는 않는다. 연결 흐름은 다음과 같다.

```text
사용자가 웹에서 결과·피드백 저장
  → 백엔드가 사용자 ID·진단 ID 기준으로 보관
  → 어드민이 해당 사용자 ID로 조회
  → 운영자가 화면에서 확인
```

2026-10-10 개발 서버의 공개 OpenAPI를 직접 조회해 HTTP 200을 받았고, 위 세 경로와 `POST /api/v1/admin/login`이 등록되어 있음을 확인했다. 프론트의 경로와도 일치한다. 이 확인은 실제 ADMIN 로그인 후 데이터 조회 성공과는 구분한다.

## 4. 작업 단위 C — 페이지 이동·새로고침·데이터 검증

- 한 페이지에 10건을 표시하고 전체 건수, 현재/전체 페이지, 이전·다음 버튼을 제공한다.
- 견적에서 진단·피드백 등 다른 종류로 바꾸면 첫 페이지부터 조회한다.
- 새로고침 버튼으로 웹에서 수정된 내용을 다시 가져온다. 실시간 자동 동기화를 구현한 것은 아니다.
- 다른 사용자 상세로 이동하면 이전 사용자의 펼친 기록과 페이지 상태를 초기화한다.
- 조회 중인 사용자와 응답의 `user_id`가 다르면 기록을 표시하지 않고 오류를 안내한다.
- 필수 필드·날짜·페이지 정보가 계약과 다르면 ‘기록 없음’으로 처리하지 않고 응답 오류를 안내한다.

소유자 검증은 잘못된 응답을 화면에 표시하지 않기 위한 보조 장치다. API 접근 권한과 사용자 데이터 보호는 백엔드에서도 반드시 검사해야 한다.

## 5. 작업 단위 D — 오류와 빈 기록 구분

| 상황                           | 화면 처리                                 |
| ------------------------------ | ----------------------------------------- |
| 정상 응답, 저장 기록 0건       | 해당 종류의 저장 기록이 없다고 안내       |
| 불러오는 중                    | 로딩 상태 표시                            |
| 400 잘못된 조회 조건           | 사용자·페이지 조건 확인 안내              |
| 401 인증 만료                  | 로컬 로그인 상태 초기화, 로그인 화면 이동 |
| 403 관리자 권한 없음           | 권한이 없어 조회할 수 없다고 안내         |
| `404 USER_NOT_FOUND`           | 사용자를 찾을 수 없다고 안내              |
| 일반 404/501                   | API 연결 상태 또는 대상 확인 안내         |
| 503 저장소 장애                | 일시적인 연결 실패와 재시도 안내          |
| 500 서버 오류                  | 서버 처리 오류와 재시도 안내              |
| 응답 형식·소유자·페이지 불일치 | 데이터 표시 중단 및 원인 안내             |

‘조회에 실패했다’는 이유로 ‘이 사용자는 기록이 없다’고 표시하지 않도록 구분했다.

10월 10일 명세 수령 후에는 구체적인 백엔드 오류 코드에 맞춰 위 안내를 보완했다. 견적 금액은 기존 최소·중간·최대 객체뿐 아니라 명세 예시의 `1,000만원~1,200만원` 같은 문자열도 요약에 표시하도록 보완했다.

## 6. 작업 단위 E — 관리자 인증·로그아웃 보완

기존 관리자 로그인 화면과 로그인 API 호출을 바탕으로 인증 확인을 강화했다.

- 로그인 응답이 실제 `ADMIN`인지 확인한다.
- 보호된 화면 진입 시 `/api/v1/users/me`를 호출해 서버 세션을 확인한다. 저장된 로그인 정보만으로 관리자 화면을 보여 주지 않는다.
- 브라우저에 남은 관리자 ID와 서버가 응답한 ID가 달라지면 다시 로그인하도록 안내한다.
- 서버 로그아웃 API를 호출한다. 서버 로그아웃 실패를 성공처럼 처리하지 않고 재시도를 안내한다.
- 로그아웃하거나 로그인 계정·권한이 바뀌면 이전 계정으로 조회한 캐시를 초기화한다.

실제 서버의 관리자 계정을 생성하거나 비밀번호를 발급한 작업은 없다. 실서버 로그인에는 백엔드에 등록된 ADMIN 계정의 로그인 정보가 필요하다.

## 7. 작업 단위 F — 가상 데이터 QA 환경

백엔드 계정이나 실제 데이터 없이 화면과 오류 상태를 검토할 수 있도록 로컬 전용 QA 모드를 추가했다.

| 구분      | 실제 서버 연결 모드     | 가상 QA 모드                     |
| --------- | ----------------------- | -------------------------------- |
| 실행      | `pnpm dev:admin`        | `pnpm qa:admin`                  |
| 기본 주소 | `http://localhost:5173` | `http://127.0.0.1:5174`          |
| 데이터    | 백엔드에 저장된 데이터  | 코드에 넣어 둔 고정 예시         |
| 로그인    | 실제 ADMIN 계정         | QA 플러그인이 인정하는 가상 계정 |
| 목적      | 실제 데이터 연결 확인   | UI·페이지 이동·오류 표시 확인    |

QA에는 정상 기록, 기록 없음, 일반 404, 서버 장애, 소유자 불일치, 권한 없음, 삭제된 사용자 응답을 준비했다. 정상 예시는 견적 21건·진단 1건·피드백 2건이다.

QA 화면에는 가상 데이터임을 표시하고, 모든 API를 로컬에서 처리한다. 계정 수정·권한 변경·탈퇴 등은 QA에서 막았다. QA 모드로 운영 빌드를 만드는 것도 차단했다. 이 모드의 가상 계정과 기록은 실제 백엔드에 생성한 것이 아니다.

실제 연동 확인 중에 가상 QA 화면으로 안내한 점은 잘못된 안내였다. 실제 저장 데이터를 보려는 경우에는 5173을 사용한다.

## 8. 검증한 범위와 남은 확인

| 항목                                   | 현재 상태                                                                          |
| -------------------------------------- | ---------------------------------------------------------------------------------- |
| 어드민 자동 테스트                     | 7개 파일, 53개 테스트 통과                                                         |
| 어드민 브라우저 QA                     | 2개 시나리오 통과: 정상 조회/페이지/진단/피드백/로그아웃, 모바일 빈 기록·오류 상태 |
| 타입 검사·프로덕션 빌드                | 통과                                                                               |
| 린트                                   | 오류 없음. 기존 ToastProvider Fast Refresh 경고 1개 유지                           |
| 개발 서버 API 명세 대조                | 관리자 로그인 및 조회 3개 경로 확인                                                |
| 실제 ADMIN 로그인 → 실제 DB 기록 조회  | 아직 검증하지 못함. 실제 ADMIN 계정으로 확인 필요                                  |
| 프론트 운영 배포·운영 도메인/CORS 확인 | 이번 작업에서 수행하지 않음                                                        |

현재 제공되지 않는 데이터는 업로드 원본 파일·다운로드, 약관 동의 이력, 가입일·최근 접속 일시·접속 로그, 저장하지 않은 생성 결과, 삭제 기록 복구다. 이 정보는 전달받은 관리자 이용 내역 API 범위에 포함되지 않아 임의의 값으로 채우지 않았다. 항목별 실제 문제 여부도 사용자 요청대로 수집·표시하지 않는다.
