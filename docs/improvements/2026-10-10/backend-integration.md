## 1. 작업 단위별 변경

| QA 보강          | 피드백 API·화면 테스트, 저장·복원·수정·삭제/409/503 브라우저 시나리오. 어드민 오류별 테스트와 로컬 QA의 명세 오류 코드 반영                              | `e2e/feedback.spec.ts`, `apps/admin/qa/`                                  |

수집 범위는 **전체 평가 good/bad, 최대 3개 이유, 최대 500자 의견**이다. 항목별 실제 문제 여부는 사용자 요청에 따라 계속 제외하며 PUT에는 `item_reviews: []`를 보낸다. `report_version`은 조회 시 해당 진단 ID인지 확인하고 PUT에 포함하지 않는다. AI 서버에 피드백 저장이나 항목 ID 추가를 요청할 필요가 없다.

주요 오류 처리:

- 400: 입력 확인 안내. 401: 기존 세션 갱신/로그인 복귀 처리 사용.
- 403/404: 권한 없음/진단 없음 안내. 처음 조회 실패 시 빈 입력으로 덮어쓰지 않는다.
- 409: 최신 GET이 실패해도 초안 보존. 최신 의견을 확인하기 전까지 재전송 차단.
- 422: 처리 실패 안내, 초안 보존. 항목 리뷰는 전송하지 않는다.
- 503: 점검 안내 + 입력 보존. 복구 후 사용자가 다시 시도한다.

## 2. 지금 로컬에서 실제 API로 확인하기

### 관리자 로그인에서 막힐 때

2026-10-10 재확인: 개발 서버 `https://api-dev.muneo.kr/v3/api-docs`를 직접 조회해 HTTP 200을 받았다. `POST /api/v1/admin/login`과 사용자별 `estimates`, `risk-reports`, `feedback` GET 3개가 모두 등록되어 있고 프론트 호출 경로와 일치한다. 이는 배포 명세 확인이며 로그인 후 실제 데이터 조회 검증과는 구분한다.

- 실제 연결 화면은 `pnpm dev:admin`의 `http://localhost:5173`이다. 로그인에는 백엔드에 등록된 ADMIN 계정의 이메일·비밀번호를 사용한다.
- `admin@example.test / MuneoQa123!`는 로컬 QA 플러그인 안에서만 인정하는 가상 로그인 정보다. 실제 서버 계정으로 등록한 적이 없다.
- 배포 로그인 명세에서 401은 `INVALID_LOGIN_INFO`(이메일·비밀번호 불일치), 403은 `ADMIN_LOGIN_FORBIDDEN`(관리자 계정 아님)이다. 로그인에 실패한 경우에는 아직 사용자 이용 내역 조회 단계까지 도달하지 않은 상태다.
- 전달받은 이용 내역 문서에는 실제 계정의 이메일·비밀번호가 없다. 공개 OpenAPI의 로그인 요청 예시도 실사용 가능한 계정이라는 의미는 아니다. 필요한 확인은 API 추가 개발이 아니라 기존 ADMIN 계정 또는 사용 중인 계정의 ADMIN 권한 여부다.
- 실제 연동 확인 중에 가상 QA 화면으로 전환해도 로그인 문제는 해결되지 않는다. 가상 화면은 UI 시뮬레이션 용도로만 사용한다.

### 실행과 데이터 대조

루트에서 각 터미널로 실행한다.

```bash
pnpm dev:web
```

```bash
pnpm dev:admin
```

1. 웹 `http://localhost:3000`에 **테스트 USER 계정**으로 로그인한다.
2. 진단을 생성하고 **결과 저장**을 누르거나, `/history`에서 본인이 저장한 진단을 연다.
3. 결과 하단에서 평가·이유·의견을 작성하고 **의견 보내기**를 누른다.
4. 새로고침 → 동일 의견 복원 → **의견 수정** → 평가 변경/의견 비우기 → 전송 → 다시 새로고침한다.
5. **다른 브라우저 프로필**에서 어드민 `http://localhost:5173`에 테스트 **ADMIN 계정**으로 로그인한다. 포트가 달라도 localhost 쿠키는 공유되므로 프로필을 나눈다.
6. 사용자 목록에서 같은 테스트 이메일 검색 → 사용자 상세 → **사용자 이용 내역 → 진단 피드백 → 새로고침**. 사용자 ID·진단 ID·평가·이유·의견이 일치하는지 확인한다.
7. 웹에서 **의견 삭제 → 삭제 확인** → 어드민 새로고침. 피드백은 사라지고 견적서 진단 탭의 원래 진단은 남아 있어야 한다.

추가 확인:

- 예상 견적과 진단도 각각 생성 후 **저장**하고 어드민의 해당 탭에서 확인한다. 저장 전 결과는 조회 대상이 아니다.
- 웹은 `apps/web/.env.local`의 `NEXT_PUBLIC_API_BASE_URL`, 어드민은 `apps/admin/.env.local`의 `VITE_API_BASE_URL`을 확인한다. 어드민 개발 기본값은 `https://api-dev.muneo.kr`다. 두 앱이 같은 환경이어야 한다.
- 웹 피드백 기본값은 이제 `api`다. 과거 설정에 `NEXT_PUBLIC_DIAGNOSIS_FEEDBACK_MODE=preview` 또는 `disabled`가 남아 있으면 제거하거나 `api`로 바꾸고 **재시작/재빌드**한다.
- `/preview/diagnosis`는 계속 체험 전용이다. 여기서 입력한 의견은 서버나 어드민에 나타나지 않는다.
- `pnpm qa:admin`의 5174 화면은 고정 가상 데이터다. 실제 웹에서 제출한 의견을 확인하려면 **`pnpm dev:admin`의 5173**을 사용한다.
- 비밀번호·토큰은 QA 문서/이슈/채팅에 기록하지 않고 담당자가 직접 로그인한다.

## 3. FE · AI · BE/infra 합동 QA 개요

목표: 사용자 입력 → AI 진단 → 결과 저장 → 피드백 저장/복원/삭제 → 어드민 조회까지 같은 사용자·진단에 정확히 연결되는지 확인한다.

준비물: 동일 개발 환경의 웹/어드민/API 주소, 테스트 USER A·B 및 ADMIN 계정, 테스트 견적서 2~3개, 공통 이슈 기록판. 시작할 때 FE 커밋·BE 배포 버전·AI 버전을 기록한다. 정상 견적서, 항목 누락 견적서, 읽기 어려운 파일을 함께 준비한다.

| 단계           | 진행                                                         | 합격 기준                                                          | 담당          |
| -------------- | ------------------------------------------------------------ | ------------------------------------------------------------------ | ------------- |
| 환경/인증      | USER와 ADMIN을 다른 프로필에서 로그인, 두 앱의 API 환경 대조 | 로그인 유지, 관리자 권한 검증, 같은 환경                           | FE + BE/infra |
| 진단 생성/저장 | 파일 업로드 → 진단 → 인사이트/근거 검토 → 저장 → 내역 재진입 | 입력·원문·결과의 연결 유지, ID 확보, 저장 결과 복원                | FE + AI + BE  |
| 피드백 생성    | good/bad 각각 제출, 이유 선택, 선택 의견 생략/500자 경계     | PUT 204, DB 한 건, 해당 사용자·진단 연결                           | FE + BE       |
| 수정/복원      | 재진입 → 수정, 이유/의견 비우기 → 새로고침                   | 기존 값 제거 포함 반영, 중복 레코드 없음                           | FE + BE       |
| 어드민 대조    | 동일 사용자 견적/진단/피드백 조회 및 페이지 이동             | 웹과 ID·내용 일치, 총 건수·정렬·페이지 정확                        | FE + BE       |
| 실패/동시성    | 통제된 환경에서 400/409/503·네트워크 실패                    | 성공으로 오표시하지 않음, 초안 유지, 최신 의견 확인·재시도 가능    | FE + BE/infra |
| 소유권/권한    | USER B가 A 진단 피드백에 접근, USER로 관리자 API 접근        | 서버가 403, 다른 사용자 데이터 노출 없음                           | BE + FE       |
| 삭제           | 피드백 삭제, 별도 테스트 데이터의 진단/사용자 삭제           | 피드백만 삭제 시 진단 유지. 진단/사용자 삭제 시 명세대로 연쇄 삭제 | BE + FE       |
| AI 품질        | 같은 예시의 누락/중복/불분명 근거와 질문을 원문 대조         | 잘못된 판단·근거를 AI 이슈로 기록, 화면 분류와 원 응답 일치        | AI + FE       |

권장 순서: 환경 점검 10분 → 정상 흐름 25분 → 오류/권한/AI 검토 25분 → 이슈 분류와 재검증 담당 지정 10분. API 오류를 강제로 발생시키는 시험은 개발/테스트 환경에서 수행한다. 서버 409가 매번 재현되지 않으면 FE 시뮬레이션 검증과 BE 동시성 검증 결과를 따로 기록한다.

이슈 기록 형식:

```text
[QA-번호] 제목
환경 / FE 커밋 / BE·AI 버전:
담당: FE | AI | BE/infra
재현 순서:
예상 / 실제 결과:
테스트 사용자 ID / reportId / 발생 시각:
HTTP 상태·오류 코드 / 민감정보를 가린 화면:
심각도: 배포 차단 | 주요 기능 | 문구·표시
수정 상태 / 재검증 결과:
```

배포 판단: 정상 저장→재조회→어드민 대조→삭제 통과, 권한/소유권 차단 통과, 입력 유실·중복 저장·타 사용자 정보 노출 이슈 없음. AI 품질의 허용 기준과 개인정보/약관 초안의 미확정 사항은 각 담당자가 별도로 확정한다.

## 4. 백엔드 문서의 남은 질문

| 항목                | 현재 답변 / 필요한 확인                                                                                                                                                                                                                  | 담당          |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| 어드민 도메인       | `apps/admin`은 고객용 `apps/web`과 별도 앱이다. 로컬은 5173, 별도 배포를 지원하지만 실제 운영 어드민 도메인은 이 저장소만으로 확정할 수 없다. 실제 배포 URL을 전달해 CORS 허용 origin·credentials·쿠키 Domain/SameSite/Secure를 확인한다 | FE/infra → BE |
| 항목별 문제 여부    | 이번 수집에서 제외. `item_reviews: []`. AI 고정 item ID 도입 불필요                                                                                                                                                                      | 확정          |
| 소프트 삭제         | 기본 명세의 연쇄 삭제를 기준으로 연동. 복구/장기 보존 필요성은 미결정이며 프론트에서 보존 기능을 추가하지 않았다. 필요하면 목적·보유 기간·운영자 권한을 정한 뒤 BE와 별도 계약                                                           | 운영자 + BE   |
| 피드백 `updated_at` | 사용자 GET 예시는 시간대 없는 값, 관리자 응답은 Z가 있는 값이다. 사용자 화면에서는 시간을 표시하지 않아 임의 변환하지 않는다. 운영 기록의 일관성을 위해 offset 포함 ISO 8601 권장 여부를 확인                                            | BE            |
| 전체 사용자 데이터  | 이번 명세는 저장 견적/진단/피드백만 추가한다. 업로드 원본·약관 동의 이력·가입/접속 일시·삭제 기록 복구는 여전히 별도 계약 필요                                                                                                           | FE + BE/infra |

백엔드 전달용 짧은 문안:

> 전달해 주신 명세로 FE 연결을 반영했습니다. 기존 API 환경을 그대로 사용하고 피드백은 전체 평가/이유/의견과 item_reviews 빈 배열만 전송합니다. 어드민은 별도 프론트 앱이며 로컬 주소는 http://localhost:5173 입니다. 실제 배포 어드민 URL은 FE/infra에서 확인 후 CORS·쿠키 설정을 함께 점검하겠습니다. 테스트 USER/ADMIN으로 웹 저장→어드민 조회를 QA하고, 피드백 조회 시각의 timezone 및 소프트 삭제 필요성은 별도로 확정하겠습니다.

- 웹 Vitest: 23개 파일, 199개 테스트 통과.
- 어드민 Vitest: 7개 파일, 53개 테스트 통과.
- 웹·어드민·E2E TypeScript 검사 통과. 전체 린트 오류 없음. 기존 `ToastProvider.tsx` Fast Refresh 경고 1개 유지.
- 브라우저: 웹 주요 흐름 7개(피드백 CRUD·409·503 및 기존 개선 4개), 어드민 2개 통과. 인증 준비 테스트는 별도 통과. 모바일 삭제 확인 화면도 시각 검토했다.
- 웹 Next.js 프로덕션 빌드와 어드민 Vite 프로덕션 빌드 통과. 전체 포맷 검사 및 `git diff --check` 통과.

웹 브라우저 검증은 `화면 → Next.js 프록시 → 로컬 mock API → 저장 내용 재조회 → 화면 복원`까지 확인했다. 409/503은 브라우저 요청 가로채기로 재현했다. E2E에서 실제 화면 제목과 다른 기대값, 브라우저 도구에서 노출되지 않는 PUT 본문 검사 부분은 각각 실제 제목 대조와 API 재조회 검증으로 보완한 뒤 해당 시나리오를 재실행해 통과했다. 웹 빌드는 샌드박스 내 장시간 컴파일을 중단한 뒤 제한 밖에서 완료했다.

자동 테스트의 저장소는 로컬 mock 메모리다. 실제 PostgreSQL/MongoDB 반영과 배포 도메인의 쿠키·CORS는 테스트 계정으로 위 2~3절을 수행해야 확정할 수 있다. 이번 작업에서 실제 사용자 데이터 쓰기·FE 배포는 수행하지 않았다.
