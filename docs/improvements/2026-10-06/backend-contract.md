# 백엔드 협의안: 진단 피드백과 점검

이 문서는 **새 계약 제안**이다. 피드백 저장 API는 아직 없으며 사용자가 백엔드에 신규 개발을 요청할 예정이다. 아래 내용을 요청서로 전달하면 된다. 클라이언트는 기본적으로 비활성이고 미리보기는 네트워크 요청을 보내지 않는다.

## 피드백 단위와 저장 규칙

- 기본 단위는 로그인 사용자 + 저장된 진단 결과 ID다. 진단 저장 API가 반환하는 `id`를 사용한다.
- 진단 분석 API는 아직 저장 전 결과 ID를 주지 않는다. 따라서 서버 연동 모드에서는 결과를 먼저 저장해야 의견을 전송한다. 프론트는 저장 후에도 결과 화면을 유지한다.
- 수집 범위는 전체 만족도 `good`/`bad`, 선택 이유, 자유 의견이다. 사용자 요청에 따라 항목별 실제 문제 여부는 받지 않는다.
- 사용자 ID는 브라우저 본문의 값을 신뢰하지 말고 세션에서 판별한다. 다른 사용자의 결과에 제출할 수 없어야 한다.
- 동일 사용자·결과에 대한 PUT은 한 레코드를 갱신한다. 재전송·연속 클릭으로 중복 데이터가 생기지 않아야 한다.
- 분석 결과를 다시 생성하면 새 report ID를 사용하거나 명시적인 `report_version`을 발급한다. 과거 피드백이 다른 진단 결과에 연결되지 않게 한다.

## 프론트에 준비한 PUT

```http
PUT /api/v1/risk-detector/{report_id}/feedback
Content-Type: application/json
Cookie: access_token=...
```

```json
{
  "schema_version": 1,
  "rating": "bad",
  "reasons": ["incorrect_result", "unclear_explanation"],
  "comment": "확인할 내용을 찾는 데 도움이 됐지만 설명이 조금 어려웠어요."
}
```

성공은 `204 No Content`를 권장한다. 프론트는 2xx 여부만 확인하며 응답 본문을 요구하지 않는다. 오류는 현재 API 형식의 `code`, `message`와 HTTP 상태를 사용한다.

| 필드           | 검증                                                             |
| -------------- | ---------------------------------------------------------------- |
| schema_version | 1                                                                |
| rating         | good 또는 bad, 필수                                              |
| reasons        | 평가에 맞는 enum, 중복 제거, 최대 3개, 선택                      |
| comment        | trim 후 최대 500자, 선택, 연락처·주소 등 개인정보 입력 금지 안내 |

good 이유: `found_risks`, `clear_explanation`, `useful_questions`.
bad 이유: `incorrect_result`, `missing_risks`, `unclear_explanation`.

예상 오류: 400/422 입력 검증, 401 인증, 403 소유권, 404 결과 없음, 409 결과 버전 충돌, 429 요청 제한, 503 점검. 실패 시 프론트는 내용을 유지하며 성공으로 표시하지 않는다.

## 진단 결과 식별자와 조회 계약: 활성화 전 확정 필요

피드백은 저장된 진단 결과의 `id`에 연결한다. 항목별 기록을 수집하지 않으므로 개별 공정·항목의 고정 ID를 피드백 API의 선행 조건으로 요청하지 않는다. 진단 결과 ID의 소유권과 결과 재생성 시 새 ID 또는 버전 부여 규칙을 확정한다.

다음 확장이 권장된다. 아래 GET/DELETE는 이번 프론트에 연결하지 않았다.

```http
GET /api/v1/risk-detector/{report_id}/feedback
DELETE /api/v1/risk-detector/{report_id}/feedback
```

GET: 미작성 시 204, 작성 시 PUT 데이터 + `updated_at`, `report_version`. 이를 받으면 이력 화면에서 기존 평가·이유·의견 복원이 가능하다. 현재 UI 상태는 화면을 떠나면 사라지고 api 모드의 새 PUT은 전체 교체한다. 기존 기록을 모르고 덮어쓰는 것을 막기 위해 운영 활성화 전에 GET 조회와 버전 충돌 정책까지 연결해야 한다. DELETE: 본인 철회, 204. 리포트 삭제·탈퇴 때 피드백의 연쇄 삭제/익명화 정책도 결정한다.

## 서버 작업 목록

1. 피드백 테이블과 사용자/리포트 고유 제약, 로그인 세션 기반 소유권 검사.
2. 저장된 리포트 ID와 결과 재생성 시 버전 처리 규칙 제공.
3. PUT 저장/수정 및 입력 검증, GET 복원, DELETE 철회.
4. 관리 화면 지표: 응답률, good/bad 비율, 선택 이유 분포.
5. 자유 의견의 운영 열람 권한·보유 기간·탈퇴 삭제·감사로그. 자유 의견/업체명/원문은 GA로 보내지 않는다.
6. 단순 사용자 평가를 모델 학습에 자동 투입하지 않는다. 활용 목적과 검수·개인정보 처리 방침을 먼저 확정한다.

## 실제 저장 확인 절차

계약 완료 → GET 복원 구현 → `NEXT_PUBLIC_DIAGNOSIS_FEEDBACK_MODE=api`로 재빌드 → 실제 계정으로 진단/저장 → good/bad 전송 → 네트워크 요청·응답 확인 → DB 한 레코드 확인 → 새로고침 후 조회값 복원 확인 → 수정/실패/중복/타인 결과 접근/삭제를 테스트한다. 현재 자동 테스트는 API 호출 계약과 UI 동작을 mock으로 검증한다.

## 점검/인증 협의

공개 `GET /health/ready` (예시 경로)를 요청한다. 정상 200, 점검/필수 의존성 장애 503, `Cache-Control: no-store`, `Retry-After`를 반환한다. 진단 모델·DB·파일 처리 중 어떤 의존성을 검사하는지 구분한다. 인증이 필요한 엔드포인트를 readiness 대용으로 사용하지 않아도 되도록 제공한다.

로그인·가입·소셜 가입에서 HttpOnly 쿠키 발급과 `/users/me` 확인 시점을 일관되게 한다. 갱신 실패의 401/403은 세션 만료, 5xx/연결 실패는 장애로 분리한다. SSR proxy 갱신 쿠키의 Domain/Secure/SameSite 및 같은 요청 내 `/me` 전달을 실제 배포 도메인에서 확인한다.

## 견적 입력 협의

- 화장실 개수는 기존 `욕실.개수`에 반영한다. 욕실 공정을 선택하지 않으면 새로운 최상위 필드를 보내지 않는다.
- `거주중공사`와 `공사시기`, `트럭접근`, 건물 연식의 실제 금액 보정 여부/계수를 확인한다. 사용하지 않는 입력은 UI와 필수값에서 함께 제거한다.
- 철거 범위 세부값은 기존 매핑이 전송하지 않아 이번 화면에서 제외했다. `철거여부`와 선택 공종은 유지한다.
- 일반/브랜드/규격별로 최소 사례 수를 정하고, 데이터 부족 시 0원을 실제 견적처럼 표시하지 않는 계약을 유지한다.
