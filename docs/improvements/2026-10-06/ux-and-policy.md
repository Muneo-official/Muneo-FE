## 이용약관 페이지 기획

`/terms`에 목적·용어·계정·서비스 범위·이용 제한·저작물·중단/변경·탈퇴·문의/분쟁·시행일/변경 이력을 둔다. 가견적은 확정 견적이 아니며 진단은 확인 보조라는 점, 실제 공사 계약은 사용자와 시공업체 사이에서 확인한다는 점을 쉬운 문장으로 설명한다. 과도한 전면 면책이나 이용자 권리 제한을 임의로 넣지 않는다.

핵심 내용은 한국어로 알아보기 쉽게 표시하고 계약 체결 때 약관을 확인할 수 있게 제시한다. [약관법 제3조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1021562635)를 바탕으로 화면을 설계하고 최종 책임·분쟁 조항은 실제 운영 조건에 맞게 검토한다.

서비스별 결정 사항:

- 현재 무료 범위와 향후 유료 기능 도입 시 별도 고지 방식.
- AI 결과의 근거·데이터 부족·정확도 한계 설명. 검증되지 않은 정확도 수치는 쓰지 않는다.
- 견적서 업로드 권한, 제3자 개인정보 마스킹, 콘텐츠 보유·삭제 범위.
- 점검/장애 시 고지, 복구 확인, 진행 중 요청 및 결과 저장 실패 처리.
- 정상 사용자 이용 제한의 사유·통지·이의 제기 경로.
- 회원 탈퇴 및 데이터 삭제/보존 예외와 통지.

## 가입 동의 UX와 API 제안

처리방침 공개와 개인정보 수집·이용 동의는 목적이 다르다. 실제 처리의 법적 근거를 확정한 후 필요한 동의만 받는다. ‘처리방침에 모두 동의’ 하나로 모든 처리 목적을 덮지 않는다.

권장 UI: `[필수] 이용약관 동의` + 수집·이용 동의가 필요한 경우 해당 목적/항목/기간/거부 영향 안내 + 실제 마케팅을 운영할 때만 별도 `[선택] 마케팅 동의`. 모두 미선택으로 시작하고 필수 항목만 가입 조건으로 삼는다. 상세 전문은 입력값을 유지한 채 새 탭/접근 가능한 대화상자로 제공한다.

백엔드 제안:

```json
{
  "agreements": [{ "type": "terms", "version": "확정된_버전", "agreed": true }]
}
```

서버가 현재 필수 문서 버전을 검증하고 동의 시각·사용자·문서 버전을 저장한다. 처리 근거와 목적에 따라 필요한 추가 동의 타입을 합의한다. 프론트 로컬스토리지만으로 동의 증적을 대신하지 않는다. 이메일 가입과 소셜 가입을 같은 계약으로 처리한다. 약관 버전 변경, 필요한 재동의, 동의 철회/탈퇴도 포함한다.

## 공개 전 남은 작업

현재 `/privacy`, `/terms` 초안과 푸터·가입 화면 링크를 구현했다. 다음 순서는 미확정 운영 정보 확인 → 본문 확정 → 시행일·최종 버전 반영 → 필요한 동의 API와 프론트 연결 → 이메일·소셜 가입 회귀 테스트 → 배포다. 초안 열람은 약관 동의로 처리하지 않는다.
